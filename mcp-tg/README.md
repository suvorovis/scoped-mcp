# mcp-tg

Read-only MCP-сервер для Telegram. Claude читает сообщения только из чатов, перечисленных в конфиге явно (`chats`) или добавленных в указанные там папки Telegram (`folders`). Запись, отметка «прочитано», доступ к другим чатам, профилю и контактам невозможны: каждый исходящий RPC проходит через middleware с белым списком методов и проверкой peer.

## Установка и настройка

Пошагово, от получения ключей API (включая обход ограничений из РФ) до работы в Claude Code и смены списка чатов, — в [SETUP.md](SETUP.md).

Кратко: `make install-mcp-tg` из корня scoped-mcp (сборка, установка в `$(go env GOPATH)/bin` и подпись с hardened runtime) → `~/.config/mcp-tg/config.yaml` с ключом `secrets: keychain | file | env` → `mcp-tg login` (в режиме `keychain` сам создаст связку ключей и спросит `api_id`/`api_hash`; в режиме `env` ключи берутся из `MCP_TG_API_ID`/`MCP_TG_API_HASH`) → чаты из `mcp-tg dialogs` в `chats` и/или папки из `mcp-tg folders` в `folders` → `mcp-tg serve` в `.mcp.json` или через `claude mcp add`.

`login` и `dialogs` работают без guard (middleware с белым списком RPC и проверкой peer, см. «Гарантии»). `folders` работает с отдельным folder-guard (см. «Гарантии»). Все три допускают пустые `chats` и `folders`. `serve` требует, чтобы хотя бы один из списков `chats` или `folders` был непуст, и сохранённую сессию (`mcp-tg login`).

## Конфиг

```yaml
secrets: keychain
keychain_path: ~/Library/Keychains/scoped-mcp.keychain-db
chats:            # может быть пустым или отсутствовать, если заданы folders
  - id: 1234567890
    type: channel
    access_hash: 8812345678901234
    title: Team oncall
folders:
  - id: 3
    title: Claude   # подсказка для человека
```

- `secrets` — где лежат ключи API и сессия MTProto: `env`, `file` или `keychain`. Без строки `secrets` — режим `env`. Каждому режиму нужен свой ключ пути, он и его значение по умолчанию — в таблице раздела «Хранение секретов»; ключи путей других режимов не используются.
- `chats` — явный список, записи печатает `mcp-tg dialogs`.
- `folders` — папки Telegram по `id` (стабилен при переименовании), записи печатает `mcp-tg folders`. Из папки берутся только явно добавленные в неё чаты (`include_peers` и закреплённые `pinned_peers` за вычетом `exclude_peers`). Типы чатов из настроек папки (Контакты, Не контакты, Группы, Каналы, Боты) и исключения (Без звука, Прочитанные, Архив) игнорируются: чтобы получить список их чатов, нужен `messages.getDialogs`, который отдаёт все диалоги аккаунта. У папки с такими категориями `mcp-tg folders` печатает внутри записи комментарий об этом. «Избранное», даже добавленное в папку поимённо, не читается и явным чатом не считается. Папка без явных чатов или с несуществующим `id` — ошибка запуска `serve`, не пустой доступ. Общие папки (добавленные по ссылке-приглашению) раскрываются так же: в них учитываются только чаты, в которые вы вступили.
- Служебный чат «Telegram» (`user` с id `777000`) никогда не добавлять ни в `chats`, ни в папку: через него приходят коды входа в аккаунт.
- Итоговый список разрешённых чатов — `chats` плюс чаты папок без повторов по паре (тип, id); при совпадении остаётся запись из `chats` с её `title`.
- Состав папок читается один раз при старте `serve`: новый чат в папке начинает читаться после Reconnect сервера в `/mcp`.

## Хранение секретов

Секреты сервера — `api_id`, `api_hash` и сессия MTProto (`session`). Сессия меняется во время работы (Telegram обновляет её), поэтому её хранилище должно поддерживать запись.

| `secrets` | ключ пути в конфиге (по умолчанию) | `api_id`, `api_hash` | сессия | от кого защищает |
|---|---|---|---|---|
| `env` (по умолчанию) | `session_path` (обязателен, умолчания нет) | переменные `MCP_TG_API_ID`, `MCP_TG_API_HASH` | файл `session_path` с правами `0600` в каталоге `0700` | только от других пользователей машины |
| `file` | `secrets_dir` (`~/.config/mcp-tg/secrets`) | файлы `api_id`, `api_hash` в `secrets_dir` (`0700`/`0600`) | файл `secrets_dir/session` | только от других пользователей машины |
| `keychain` (macOS) | `keychain_path` (`~/Library/Keychains/scoped-mcp.keychain-db`) | элементы с service `mcp-tg` и account `api_id`, `api_hash` в связке `keychain_path` | элемент с service `mcp-tg` и account `session` там же | от любого процесса того же пользователя без пароля связки, включая агента |

Права в режимах `env` и `file` проверяются при каждом чтении: каталог или файл секрета, доступный группе или остальным, останавливает `serve`, `login`, `dialogs` и `folders` с ошибкой `file: secret must not be accessible by group or others: <путь> has mode <режим>`. В режиме `env` это касается и каталога `session_path` (обычно `~/.config/mcp-tg`): ему нужен `chmod 700`.

`keychain` — отдельная связка ключей `~/Library/Keychains/scoped-mcp.keychain-db`, одна на все MCP (mcp-tg, mcp-jira, …). Элементы разных MCP различаются атрибутом service, у mcp-tg это `mcp-tg`; account — имя секрета, метка элемента — `mcp-tg: <account>`. В список поиска пользователя связка не добавляется: `security find-generic-password` без явного пути её не видит.

Доступ к элементу macOS выдаёт только бинарям из ACL элемента (по хешу подписи): создавшему его и разрешённым кнопкой «Разрешать всегда». Любой другой процесс получает **диалог доступа к элементу связки** — «mcp-tg хочет использовать… введите пароль связки scoped-mcp» (вместо mcp-tg — имя запросившей программы) с кнопками «Разрешать всегда», «Разрешить» и «Отказать».

Автоблокировка связки выключена: она запирается только при перезагрузке. После перезагрузки первое обращение к ней показывает **диалог разблокировки связки** — «… хочет использовать связку ключей «scoped-mcp»…» с паролем связки. Это ожидаемый диалог, его можно проходить в любой момент после перезагрузки; шаги — в [SETUP.md](SETUP.md), «После перезагрузки (только keychain)».

Связку создаёт `mcp-tg login` (печатает `Creating keychain <путь>: choose its password in the macOS dialog`); пароль задаётся в системном диалоге и через процесс mcp-tg не проходит. Миграции сессии из файла в связку нет: после смены `secrets` — новый `mcp-tg login`.

`mcp-tg dialogs` и `mcp-tg folders` остаются в том же доверенном бинаре: любой, кто может его запустить, включая агента, увидит названия и id всех чатов аккаунта мимо allowlist. Это принято; сессию и ключи он так не получит — они остаются внутри процесса mcp-tg.

### Подпись бинаря

`make install-mcp-tg` подписывает бинарь ad-hoc с hardened runtime (`codesign -s - -f -o runtime`). Это нужно по двум причинам: процесс с hardened runtime закрыт от подключения отладчика и от `DYLD_INSERT_LIBRARIES` (секреты нельзя вытащить из памяти работающего сервера), а ACL элементов связки доверяет хешу кода (cdhash) именно подписанного бинаря. Поэтому подпись должна быть на месте до первого обращения к связке: `mcp-tg login` запускать уже установленным через `make install-mcp-tg` бинарём.

Каждая пересборка даёт новый cdhash: после очередного `make install-mcp-tg` первое обращение к каждому элементу (`api_id`, `api_hash`, `session`) показывает диалог доступа к элементу связки. Правило обновления и как проходить этот диалог — в [SETUP.md](SETUP.md), «Обновление mcp-tg».

### Чек-лист проверки ACL

1. Заблокировать связку (`security lock-keychain ~/Library/Keychains/scoped-mcp.keychain-db`) и запустить установленный `mcp-tg serve </dev/null`: появляется диалог разблокировки связки. Нажать «Отменить»: ожидается ошибка `keychain: access denied` (без пароля элемент не читается).
2. Разблокировать (`security unlock-keychain ~/Library/Keychains/scoped-mcp.keychain-db`) и повторить: `serve` завершается без диалогов и без ошибки в stderr (бинарь в ACL элементов).
3. `security find-generic-password -s mcp-tg -a session -w ~/Library/Keychains/scoped-mcp.keychain-db`: появляется диалог доступа к элементу связки — чужому процессу элемент без пароля не отдаётся. Нажать «Отказать».
4. Из корня scoped-mcp `make build-mcp-tg && ./bin/mcp-tg serve </dev/null`: тот же диалог доступа к элементу связки для пересобранного бинаря. Нажать «Отказать».

## Инструменты

| Инструмент | Параметры |
|---|---|
| `list_chats` | — |
| `list_topics` | `chat_id` |
| `get_messages` | `chat_id`, `topic_id?`, `limit?` (50, max 100), `before_id?`, `since?` (RFC 3339) |
| `search_messages` | `chat_id`, `query`, `topic_id?`, `limit?`, `before_id?` |

Ответ `get_messages`/`search_messages` содержит `next_before_id`, если сообщения, возможно, ещё есть.

## Гарантии

- Белый список RPC основного подключения: `messages.getHistory`, `messages.search`, `messages.getReplies`, `messages.getForumTopics`, `messages.getPeerDialogs`, `help.getConfig`. Всё остальное, включая `messages.getDialogFilters`, отклоняется до отправки.
- Папки раскрываются (превращаются в список чатов) при старте `serve` отдельным первым подключением с folder-guard, пропускающим только `messages.getDialogFilters` и `help.getConfig`; оно завершается до старта основного. Инструменты MCP работают только в основном подключении и состав папок перечитать не могут.
- Peer каждого запроса сверяется с итоговым списком (`chats` плюс чаты папок) по паре (тип, id).
- Комментарии к посту канала читаются, только если привязанная группа обсуждения тоже есть в итоговом списке (в `chats` или в одной из папок): guard сверяет peer каждого сообщения в ответе `messages.getReplies`; если хотя бы один не из итогового списка, отклоняется весь ответ.
- `serve` не вызывает методов, отмечающих сообщения прочитанными. Guard в `serve` включён всегда, флага отключения нет.
- В `serve` stdout занят протоколом MCP. В stderr попадает только ошибка, с которой `serve` завершился (например, подсказка запустить `mcp-tg login`). Отказы guard и прочие ошибки инструментов в stderr не пишутся: модель получает их ответом `tools/call` с `isError`.
- При отозванной сессии (`AUTH_KEY_UNREGISTERED`) `serve` завершается с подсказкой запустить `mcp-tg login`, в том числе если сессия отозвана к моменту раскрытия папок.
- В режиме `keychain` ключи и сессия читаются только бинарём из ACL элемента: создавшим его или разрешённым через «Разрешать всегда». Другой процесс того же пользователя получает диалог доступа к элементу связки с паролем связки. Ни одна ошибка сервера не содержит значения секрета.

## Ручная проверка

Нужны настоящий аккаунт Telegram, `api_id`/`api_hash` и доступ к телефону за кодом.

Режим `env`: перед проверкой `export MCP_TG_API_ID=... MCP_TG_API_HASH=...`. Режим `keychain`: вместо `./bin/mcp-tg` запускать установленный `mcp-tg` (после `make install-mcp-tg`) — элементы, созданные `./bin/mcp-tg`, доверяли бы этому бинарю, и установленный `mcp-tg` получил бы диалог доступа к элементу связки (см. «Подпись бинаря»). Команды — из корня scoped-mcp.

```bash
make build-mcp-tg
./bin/mcp-tg login              # телефон, код, пароль 2FA
./bin/mcp-tg dialogs | head     # YAML с id/type/access_hash/title
./bin/mcp-tg folders            # YAML с id/title папок; у папок с категориями — строка-комментарий
```

В режиме `env` после `login` — `ls -l ~/.config/mcp-tg/session.json` даёт `-rw-------`.

Перенести один-два чата в `chats` конфига и/или одну папку в `folders`, затем:

```bash
{ printf '%s\n' \
    '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"probe","version":"0"}}}' \
    '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
    '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"list_chats","arguments":{}}}'
  sleep 15; } | ./bin/mcp-tg serve
```

`sleep` держит stdin открытым: на конце ввода MCP SDK закрывает соединение, и ответы на ещё не обработанные запросы теряются.

Ожидается: ответ на `tools/call` (`"id":2`) без `isError`, в нём чаты из конфига с живыми названиями из Telegram. Если вместо них пришли `title` из конфига (или пустые названия), запрос к Telegram не удался: `list_chats` тогда отдаёт чаты из конфига без `isError`, а `serve` ошибку в stderr не пишет.

После подключения к Claude Code проверить:

- чтение разрешённого чата через `get_messages`;
- `list_chats` показывает чаты из папки вместе с чатами из `chats`, без дублей;
- чтение чата, который есть только в папке;
- отказ на чат, которого нет ни в `chats`, ни в папках;
- сообщения, полученные через сервер, остаются для собеседников непрочитанными.

## Разработка

Из корня scoped-mcp:

```bash
make generate          # mockgen
make lint              # golangci-lint v2 через go tool
make test
make build-mcp-tg      # bin/mcp-tg
make install-mcp-tg    # только с чистого дерева scoped-mcp: go mod verify, go install -mod=readonly, codesign с hardened runtime
GOOS=linux go build ./...   # заглушка keychain для других ОС
```

`make generate`, `make lint` и `make test` проходят по всем серверам монорепозитория.

Библиотека секретов — общая для всех серверов `pkg/secret` в корне scoped-mcp. Её тесты `pkg/secret/keychain` создают связки во временных каталогах с выключенными диалогами (`SecKeychainSetUserInteractionAllowed(false)`) и login keychain не трогают.
